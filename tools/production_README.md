## What runs, and what it writes

```
 daily 03:00 Sydney (job dq_daily, paused until you unpause it)
   run_checks   jobs/run_checks.py         -> results.check_run, results.violation_sample
      |            reads the 5 source tables (current records only, see 05)
      v
   triage       notebooks/03 (model call)  -> results.cohort
                   only breaches that escalate; exits cleanly when there are none

 on demand (job dq_tolerance_advice)
   advise       notebooks/06 (model call)  -> results.tolerance_proposal
```

Nothing writes a source table. The jobs append only to tables in `{cat}.{sch}`.

**Until a rule is promoted, triage writes nothing.** All the rules are registered in
shadow: the checks job measures them and records `skipped`, and a shadow rule never
breaches. Promotion is step 5, and it is a person's decision.

## Setup, once

Run the SQL in the SQL editor on a SQL warehouse, one file at a time, in order. Every file
apart from `01` is safe to re-run.

1. **`sql/00_preflight.sql`**: who you are, and whether you can create views and functions
   in `{cat}.{sch}`. It also checks that our tables are not there yet, that the five source
   tables can be read, and that the CDC columns exist. Every statement should succeed and
   every "EXPECTED: zero rows" should be zero. Ask for the missing privilege before going
   on. A source table you cannot read becomes an `error` on every one of its checks.
   Also check in **Serving → Endpoints** that `{model}` exists.
2. **`sql/01_ddl.sql`**, **once**. It creates the tables, constraints, helper functions
   and views. `ADD CONSTRAINT` fails on a second pass. If it stops partway, fix that
   statement and continue from its banner.
3. **The register.**
   * `02_key_attributes.sql` adds the 22 key attributes, their rules (shadow) and the five
     tables selected.
   * `03_tolerances.sql` sets a placeholder tolerance per attribute, which decides what
     escalates.
{source_step}   * `05_current_records.sql` makes checks read the newest version of each record and
     drop deletions.

   Read the `EXPECTED` comment under each check query.
4. **Deploy the jobs.** You need the Databricks CLI with a profile for this workspace
   (`databricks auth login --host https://<workspace> --profile sandpit`). From
   `production/`:

   ```bash
   databricks bundle validate -t sandpit -p sandpit
   ```

   ```bash
   databricks bundle deploy -t sandpit -p sandpit
   ```

   ```bash
   databricks bundle run dq_daily -t sandpit -p sandpit
   ```

   The first run measures every rule in shadow. Expect `run_checks` to succeed and
   `triage` to exit with "no escalating breaches". Check it with `sql/07_verify.sql`:
   * 7a should show the checks as `skipped`.
   * 7b should have no errors. If it has some, they are almost always read access to a
     source table or a missing column.
   * 7c should show current records well below table rows.

   Without the CLI, make the same job by hand: **Jobs → Create job**.
   * Task 1 is a *Python script* running `jobs/run_checks.py` on serverless, with the
     parameters in `resources/dq_pipeline.yml`.
   * Task 2 is a *Notebook* task on `notebooks/03_group_and_advise.ipynb`. It depends on
     task 1. Give it an environment with the `openai` dependency, and the parameter
     `triage_job_run_id` = `{{{{job.run_id}}}}`.
5. **Promote: `sql/06_promote.sql`.**
   * Read 6a first: each shadow rule's latest measurement. A rule flagging most of its
     table is more likely a wrong rule than bad data.
   * Narrow 6b to the rules you mean, starting with one table, and run it. Your name goes
     on every promoted version.
6. **Run `dq_daily` again.** The active rules can now breach. Breaches outside their
   attribute's tolerance (and every `P1_block`) reach the triage notebook, which writes
   `results.cohort`. Check the result with 7d and 7e.
7. **Unpause the schedule** once a run is clean:

   ```bash
   databricks bundle deploy -t sandpit -p sandpit --var daily_schedule=UNPAUSED
   ```

The bundle deploys in `development` mode, so job names carry a `[dev <you>]` prefix and
run as you. Your grants are what the jobs have.

## Things that will look wrong and are not

* **Counts are higher than the migration analysis PDF.** The analysis read only records in
  migration scope (`migration_scope_flag = 1`). Nothing here applies that scope yet: it
  needs a membership slice on a pipe-delimited column, which is not built.
* **One bad value can fail two rules.** The analysis's categories were mutually
  exclusive and the rules are not.
* **The two estate rules read `STATUS = '5'` as deceased.** That value is unconfirmed.
  Check it before promoting them.
* **Every cohort reads `awaiting_triage`.** Without the app nobody records a decision, and
  the notebook does not open the decision chain it creates.

## Not in this folder

The app (`dq-app/`) and everything only an app write starts: onboarding and its steps job
(triggered by app appends), notebook 04 (mails on an accepted review), and in-app
promotion, review and tolerance decisions. Without the app, `06_promote.sql` is the
promotion, and changes to the register are SQL appends signed by whoever runs them.
